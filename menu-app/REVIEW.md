# React 3일 복습 체크리스트

> 앱 네 개를 만들면서 React가 화면을 그리고 다시 그리는 방식을 이해하고,
> **AI가 만든 React 코드에서 증상을 보고 원인을 지목**할 수 있다.

> **이 과정의 목표**
> 코드를 처음부터 작성하는 능력보다, **AI가 생성한 코드를 읽고 오류의 원인을 지목해 지시하는 능력**을 기른다.
> 아래 항목 중 ★ 표시는 AI가 만든 코드에서 특히 자주 틀리는 것이다.

제목 옆 대괄호는 학습 순서다. `[4일차]`는 3일 안에 보지 않아도 된다.

각 앱 폴더의 가이드(`01_GUIDE.md` 같은 파일)에 **학습 목표**와 **완성 확인 목록**이 따로 있다.
여기는 그 둘을 한 자리에서 복습하고, 증상으로 자료 위치를 찾는 색인이다.

## 01_react-basics — React 기본  [1일차]

### 00. React를 쓰는 이유 (`00_why-react/`)
- [ ] 같은 화면을 직접 DOM으로 그릴 때와 React로 그릴 때 코드가 어떻게 다른지 말할 수 있다.
    - [ ] `01_vanilla-dom.html`: 무엇이 바뀌었는지 개발자가 직접 계산해서 고친다
    - [ ] `02_react-createElement.html`: 상태를 바꾸고, 무엇을 고칠지는 React가 계산한다
- [ ] ★ React가 화면을 고치는 순서를 설명할 수 있다. (상태 변경 → 다시 그림 → 달라진 곳만 DOM 반영)
- [ ] JSX가 결국 `React.createElement` 호출이라는 것을 안다.

### 01. JSX
- [ ] ★ 반환값이 하나여야 한다는 것과, 그래서 `<>...</>`로 감싼다는 것
- [ ] `class`가 아니라 `className`, `for`가 아니라 `htmlFor`를 쓴다.
- [ ] 중괄호 `{}` 안에는 **표현식**(값으로 치환될 수 있는 식)만 들어간다. `if` 문은 못 들어간다.
    - [ ] 조건부 렌더링을 삼항 연산자와 `&&`로 쓸 수 있다.
    - [ ] ★ `&&` 왼쪽에 숫자 `0`이 오면 화면에 `0`이 그대로 찍힌다는 것
- [ ] 태그를 반드시 닫아야 한다는 것 (`<input />`)

### 02. 컴포넌트와 props (`complete/src/components/`)
- [ ] 컴포넌트 이름이 **대문자로 시작**해야 하는 이유를 안다.
- [ ] `props`로 값을 내려보낼 수 있다.
    - [ ] ★ `props`가 **값이 아니라 객체 하나**로 온다는 것
    - [ ] 통으로 받는 형태 (`function Header(props)` 뒤 `props.title`)
    - [ ] 구조 분해로 받는 형태 (`function TodoItem({ todo, onToggle })`)
    - [ ] 둘 중 구조 분해를 쓰는 이유를 말할 수 있다. (받을 것이 늘수록 꺼내는 줄이 늘어난다)
    - [ ] ★ 함수도 `props`로 내려보낼 수 있다는 것 — 자식이 부모의 상태를 바꾸는 방법이다
    - [ ] `children`으로 태그 사이의 내용을 받을 수 있다.
- [ ] ★ `props`는 자식이 고칠 수 없다는 것

### 03. useState와 이벤트
- [ ] `const [값, set값] = useState(초기값)` 형태를 쓸 수 있다.
- [ ] ★ `set값`을 부르면 **컴포넌트 함수가 처음부터 다시 실행**된다는 것
- [ ] ★ 상태를 직접 고치면(`todos.push(...)`) 화면이 바뀌지 않는다는 것
- [ ] 이벤트를 `onClick={함수}`로 연결할 수 있다.
    - [ ] ★ `onClick={함수()}`로 쓰면 그리는 순간 실행된다는 것
    - [ ] 인수를 넘길 때 `onClick={() => 함수(id)}`로 감싸는 이유

### 04. 목록 렌더링과 key
- [ ] `map`으로 배열을 JSX 목록으로 만들 수 있다.
- [ ] ★ `key`를 주는 이유를 설명할 수 있다. (React가 어느 항목이 그대로인지 알아보는 표시)
- [ ] ★ `key`에 배열 인덱스를 쓰면 안 되는 이유를 안다. (중간을 지우면 뒤 항목의 번호가 밀린다)

### 05. 불변성 (★ 1일차에서 가장 중요하다)
- [ ] 배열을 새로 만들어 상태를 바꿀 수 있다.
    - [ ] 추가 : `[...todos, 새항목]`
    - [ ] 삭제 : `todos.filter(...)`
    - [ ] 수정 : `todos.map(t => t.id === id ? { ...t, done: !t.done } : t)`
- [ ] ★ `push`, `splice`, `sort`, `reverse`를 상태에 쓰면 안 되는 이유를 말할 수 있다.
- [ ] 객체 안의 값 하나만 바꿀 때 `{ ...obj, key: 값 }`을 쓸 수 있다.

## 02_api-viewer — 서버 데이터  [2일차]

### 01. useEffect
- [ ] 화면을 그린 **뒤에** 실행된다는 것을 안다.
- [ ] ★ 의존성 배열의 뜻을 설명할 수 있다. — "이 값이 바뀌면 다시 해라"
    - [ ] `[]` : 처음 한 번만
    - [ ] `[id]` : `id`가 바뀔 때마다
    - [ ] ★ 배열을 아예 빼면 : 그릴 때마다 매번 → 요청이 끝없이 반복된다
- [ ] 정리 함수(`return () => {...}`)가 언제 불리는지 안다.
    - [ ] ★ 응답이 늦게 도착했을 때 이미 사라진 화면의 상태를 바꾸지 않도록 막는 용도

### 02. 서버 요청 (`starter/src/api/emoji.js`)
- [ ] `fetch`와 `axios`의 차이를 말할 수 있다.
    - [ ] `fetch`는 404여도 예외를 던지지 않아 `response.ok`를 직접 봐야 한다는 것
    - [ ] `axios`는 JSON 변환이 되어 있고 에러 상태를 예외로 던진다는 것
- [ ] ★ 요청 코드를 컴포넌트가 아니라 `api/` 폴더에 두는 이유를 안다.

### 03. 네 갈래 화면 (★ AI가 가장 자주 빠뜨린다)
- [ ] 로딩 · 에러 · 빈 결과 · 정상을 모두 처리할 수 있다.
- [ ] ★ 정상 경로만 있는 코드를 보고 무엇이 빠졌는지 지적할 수 있다.
- [ ] `try` / `catch` / `finally`로 세 상태를 관리할 수 있다.

### 04. useMemo
- [ ] 거른 결과를 상태로 따로 두지 않고 계산해서 쓰는 이유를 안다.
- [ ] ★ 상태가 둘이면 서로 어긋날 수 있다는 것 — 원본 하나만 상태로 둔다
- [ ] `useMemo`가 의존성이 그대로면 다시 계산하지 않는다는 것
- [ ] ★ 여기서는 `keyword`가 의존성이라 `useMemo`로 절약되는 것이 거의 없다는 것 — 진짜 쓰임은 앱 4에서 나온다

## 03_list-detail — 라우팅  [2일차]

### 01. react-router (`starter/src/App.jsx`)
- [ ] `BrowserRouter`, `Routes`, `Route`의 역할을 구분할 수 있다.
- [ ] `path="/pokemon/:id"`처럼 주소에 자리를 만들 수 있다.
- [ ] `path="*"`로 없는 주소를 받을 수 있다.
    - [ ] ★ 순서가 상관없다는 것 — react-router는 가장 잘 맞는 경로를 고른다

### 02. Link와 useNavigate
- [ ] ★ `Link`와 `<a href>`의 차이를 말할 수 있다. (페이지를 새로 받는가, 화면만 갈아 끼우는가)
- [ ] `useNavigate`로 코드에서 주소를 바꿀 수 있다.
    - [ ] `navigate(-1)`로 뒤로 갈 수 있다.
    - [ ] `navigate('/', { replace: true })`가 무엇을 막는지 안다.

### 03. useParams와 의존성 배열 (★ 3일 중 가장 놓치기 쉽다)
- [ ] `useParams`로 주소의 값을 꺼낼 수 있다.
- [ ] ★ 상세 화면의 `useEffect`를 `[]`로 두면 생기는 증상을 재현하고 설명할 수 있다.
    - [ ] 목록 → 상세 → 목록 → **다른** 상세로 갔을 때 앞의 내용이 그대로 남는다
    - [ ] 주소는 바뀌었는데 화면이 안 바뀐다
    - [ ] 원인 : 컴포넌트가 사라지지 않고 `id`만 바뀌었는데, 다시 부를 조건을 안 걸었다

### 04. 폴더 나누기
- [ ] `pages/`와 `components/`를 나누는 기준을 말할 수 있다.
- [ ] ★ AI도 이 구조로 코드를 만든다는 것을 안다.

## 04_form-auth — 폼과 전역 상태  [3일차]

### 01. 제어 컴포넌트 (`starter/src/pages/LoginPage.jsx`)
- [ ] `value`와 `onChange`를 짝지어 입력을 다룰 수 있다.
- [ ] ★ `value`만 주고 `onChange`를 빼면 입력이 안 되는 이유를 안다.
- [ ] ★ `onSubmit`에서 `event.preventDefault()`를 부르는 이유를 안다.
- [ ] ★ 폼 안 버튼의 `type` 기본값이 `submit`이라는 것

### 02. form Actions (`starter/src/pages/PostWritePage.jsx`)
- [ ] `<form action={함수}>` 형태를 쓸 수 있다.
- [ ] `useActionState(함수, 초기값)`가 돌려주는 셋을 설명할 수 있다. (`state`, `formAction`, `isPending`)
- [ ] ★ `formData.get('title')`이 `<input name="title">`의 `name`을 본다는 것
- [ ] `isPending`으로 저장 중 버튼을 막을 수 있다.
- [ ] 두 방식 중 무엇을 언제 쓰는지 말할 수 있다.

### 03. 쓰기 요청 (`starter/src/api/posts.js`)
- [ ] `POST` · `PUT` · `DELETE` 요청을 보낼 수 있다.
- [ ] ★ 삭제 후 목록을 `filter`로 새로 만드는 이유를 안다. (`splice`를 쓰면 화면이 안 바뀐다)
- [ ] 이 API가 실제로 저장하지 않는다는 것을 안다. **고장이 아니다.**

### 04. useContext (`starter/src/context/` 의 두 파일)
- [ ] `createContext` · `Provider` · `useContext`의 역할을 구분할 수 있다.
- [ ] 파일이 둘로 나뉜 이유를 말할 수 있다. (`AuthContext.js` 통로 / `AuthProvider.jsx` 컴포넌트)
    - [ ] 한 파일에서 컴포넌트와 컴포넌트 아닌 것을 같이 내보내면 Fast Refresh 가 깨진다는 것
- [ ] ★ `props`로 계속 내려보내는 것과 무엇이 다른지 말할 수 있다.
- [ ] ★ `useMemo`로 `value`를 감싸는 이유를 안다. **`useMemo`가 실제로 필요한 첫 자리다.**
    - [ ] 감싸지 않으면 그릴 때마다 새 객체가 되어, `useAuth`를 쓰는 컴포넌트가 전부 다시 그려진다는 것
- [ ] `RequireAuth`로 화면을 막을 수 있다.
    - [ ] ★ 이것이 **보안이 아니라 화면을 감추는 것**이라는 것 — 진짜 차단은 서버가 한다
