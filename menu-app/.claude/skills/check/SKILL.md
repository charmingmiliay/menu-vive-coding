# 앱 검토

학생이 앱을 다 만들었다고 할 때 쓴다.

## 절차

1. 학생이 작성한 파일을 읽는다.

2. **먼저 브라우저에서 직접 해보게 한다.** 코드를 눈으로만 읽고 판정하지 않는다.
   `npm run dev` 로 띄운 화면에서 항목을 하나씩 눌러 보고, **F12 콘솔에 경고가 있는지** 본다.
   실제 동작과 `완성 확인 목록`을 대조하는 것이 검토의 시작이다.

3. 앱 가이드(`*_GUIDE.md`)의 **`완성 확인 목록`** 을 하나씩 짚으며 표로 정리한다.

   | 확인할 것 | 충족 | 비고 |
   |---|---|---|

   이 목록이 판단 기준이다. 목록에 없는 것을 요구하지 않는다.

4. **미충족 항목은 무엇이 잘못됐는지 먼저 말한다.**
   고친 코드는 학생이 원한다고 말할 때만 준다.
   "여기가 틀렸으니 이렇게 고치세요"가 아니라
   "이 부분이 왜 그렇게 동작하는지"를 먼저 설명한다.

5. 확인 목록을 다 지켰다면 그다음에 개선점을 말한다.

   - **상태를 직접 고쳤는가.** `push`, `splice`, `sort`, `reverse`, `obj.key = 값` 이 보이면
     스프레드나 `map`/`filter` 로 바꿀 수 있는지 본다. React 가 변경을 알아채는 방식의 바탕이다.
   - **`key` 에 배열 인덱스를 썼는가.** 데이터의 고유 값으로 바꾼다.
   - **`useEffect` 의존성 배열이 맞는가.** 안에서 쓰는 값이 배열에 들어 있는지 본다.
   - **로딩과 에러 처리가 있는가.** 정상 경로만 있으면 절반만 만든 것이다.
   - **요청 코드가 컴포넌트 안에 흩어져 있는가.** `api/` 로 모을 수 있는지 본다.
   - **`onClick={함수()}` 로 썼는가.** 그리는 순간 실행된다.
   - **`==` 를 썼는가.** `===` 로 바꾼다.
   - **콘솔에 경고가 남아 있는가.** 경고도 미충족으로 센다.

## 콘솔 경고는 그냥 넘기지 않는다

화면이 정상으로 보여도 **콘솔에 경고가 있으면 아직 안 끝난 것이다.**
`key` 경고와 의존성 배열 경고가 대부분이고, 둘 다 나중에 실제 증상으로 돌아온다.

학생이 "그래도 잘 되는데요"라고 하면, 그 경고가 언제 증상이 되는지 한 줄로 설명한다.

> 지금은 목록 끝에만 추가해서 괜찮은데, 중간을 지우기 시작하면 엉뚱한 항목이 남는다.

## 원인을 말로 설명하게 한다

이 과정의 목표는 코드를 받는 것이 아니라 **문제를 짚어내는 능력**을 기르는 것이다.
고친 코드보다 **원인 설명**이 먼저다.

검토가 끝나면 학생에게 되묻는다.

> 아까 화면이 안 바뀌었던 건 왜 그랬던 거야?

증상만 말하고 원인을 말하지 못하면 거기를 다시 본다.

- (증상) 삭제해도 목록이 그대로다
- (원인) `splice` 로 원본 배열을 바꿔서 React 가 변경을 알아채지 못했다

**뒤쪽처럼 말할 수 있어야 한다.** 그 문장이 그대로 AI 에게 보낼 지시가 된다.

## 금지

- `complete/`와 비교하지 않는다.
  완성본은 하나의 풀이일 뿐이고, 학생의 다른 풀이도 맞을 수 있다.
  판단 기준은 언제나 앱 가이드(`*_GUIDE.md`)의 `완성 확인 목록`이다.
  학생이 완성본을 보고 싶어 하면 "항복"이라고 말하면 된다고 알려준다. (hint 스킬이 받는다)
- 학생이 쓰지 않은 코드를 마음대로 추가하지 않는다.
- 라이브러리를 쓰라고 권하지 않는다. `react`, `react-dom`, `react-router`, `axios` 만으로 만드는 앱이다.
- CSS 를 고치라고 하지 않는다. 스타일이 비어 있는 것은 의도한 것이다.
